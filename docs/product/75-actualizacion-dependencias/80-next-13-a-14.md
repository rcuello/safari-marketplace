# US-80 — Next 13.5 → 14.2 en shop y admin, con React 18

> Saca el shop y el admin de Next 13.5.6, que ya no tiene soporte, con el
> cambio más pequeño posible: la última 14.2.x, sin tocar todavía React ni
> el lint.

**Épico:** [Épico 75](./README.md)
**Fecha:** 2026-10-24
**Status:** Implementada (2026-10-24)
**Depende de:** ninguna (puede ir en paralelo con la tanda de la API)
**LOC est.:** ~150

## Historia

**Como** dueño del repo, **quiero** el frontend en Next 14.2, **para** salir
de una versión sin parches de seguridad sin abrir otros frentes.

## Contexto — verificado (2026-10-24)

- **Versión:** `next@14.2.35` pide `react ^18.2.0`, `react-dom ^18.2.0` y
  Node 18.17 o superior. `apps/shop/package.json` y
  `apps/admin/rest/package.json` declaran `"next": "13.5.6"`, con versión
  exacta.
- **Lint:** `eslint-config-next` está en 14.0.1 en las dos apps. Se sube a
  la 14.2.x que corresponda.
- **React:** `apps/package.json` fija React 18.2.0 por `resolutions`. Ver la
  D-3 del épico: con 18.2, Next 13.5 pasaba `fetchpriority` en minúscula y
  el aviso desaparecía.
- **Configuración:** los dos `next.config.js` usan `i18n` (next-i18next) e
  `images.domains`. El shop añade un `webpack` condicional, solo cuando
  `FRAMEWORK_PROVIDER=graphql`.
- **Scripts:** `next dev -p 3003` (shop, `dev:rest`), `next dev -p 3002`
  (admin) y `next lint` en las dos apps.

### Decisión del dueño (2026-10-24) — toca R-1/R-2

Con admin/graphql en `next 13.5.6`, yarn hoisteaba esa copia a
`apps/node_modules/next`, y la 14.2.35 quedaba anidada en `shop/` y
`admin/rest/`. Los paquetes hoisteados que dependen de `next` (`next-seo`,
`next-i18next`) la resolvían contra la 13.5.6. Hubo dos efectos:

- **SSR:** en el servidor, Next 14 deja `next-seo` como `external`
  (`.next/server/pages/_app.js` hace `require("next-seo")`). Su `next/head`
  era el de la 13.5.6, con otro contexto, y el HTML SSR del shop perdía
  `<title>` y las meta de `DefaultSeo` (`og:*` = 0, `next-head-count` = 2).
  Un experimento con `transpilePackages: ['next-seo']` las devolvió, lo que
  confirma el mecanismo. Se revirtió.
- **Tipos:** un TS2345 en `src/pages/_app.tsx(79,35)`. `appWithTranslation`
  esperaba el `AppProps` de la 13.5.6 ("Two different types with this name
  exist").

El dueño eligió la **opción (a)**: subir también `next`, `eslint-config-next`
y `eslint` en `apps/admin/graphql/package.json`, para que haya un solo Next.
**DA-4 se mantiene para todo lo demás**: no se exige que admin/graphql
compile.

```
$ find apps -path '*/node_modules/next/package.json' -not -path '*/node_modules/*/node_modules/*'
apps/node_modules/next/package.json 14.2.35          <- la única, en cualquier nivel
next-seo     -> apps/node_modules/next 14.2.35
next-i18next -> apps/node_modules/next 14.2.35
next-auth    -> apps/node_modules/next 14.2.35
```

### CA-3 — El lint y los tipos no empeoran ✅

```
$ cd apps/shop && yarn lint          -> ✔ No ESLint warnings or errors
$ cd apps/admin/rest && yarn lint    -> ✔ No ESLint warnings or errors
$ cd apps/shop && npx tsc --noEmit   -> 9 error TS2786, idénticos línea a línea a la base
```

Por el camino aparecieron dos problemas:

1. **TS2688 `Cannot find type definition file for 'minimatch'`.** Antes,
   `@typescript-eslint/typescript-estree@6.21.0` dejaba `minimatch@9.0.3`
   (con tipos) junto al shop, y la búsqueda secundaria de TypeScript resolvía
   por casualidad el stub `@types/minimatch@6.0.0` (lo pide `@types/glob`).
   Con la 8.72.0 hoisteada desapareció, y `tsc` moría antes de revisar el
   código (`tsc --traceResolution`). Se arregló con `"types": ["node",
   "google.maps"]`, igual que en `apps/api/rest/tsconfig.json`: son los únicos
   globales que usa el shop (`process` y `google.maps` en
   `src/lib/use-location.tsx`). Con un solo Next, el árbol vuelve a dejar un
   `minimatch@9.0.9` en `shop/node_modules`, y sin el ajuste también salen los
   9 TS2786. **Se mantiene el ajuste** para no depender de esa casualidad del
   hoisting. Si se prefiere no tocar el tsconfig, el commit `5f2f0f5` se
   revierte solo.
2. **`npx tsc` no arrancaba** mientras hubo dos Next (`MODULE_NOT_FOUND`: npx
   tomaba el shim de `shop/node_modules/.bin/tsc` por la ruta del symlink del
   workspace). Con un solo Next vuelve a funcionar (`npx tsc --version` →
   5.6.3).

### D-3 — El pin de React 18.2.0 se mantiene

Se probó en dos pasos: primero `resolutions` a 18.3.1 y después la forma
final (sin `resolutions` y 18.3.1 en las tres apps, commit `bcd6852`). Sin el
pin hay que subir también admin/graphql: si no, su 18.2.0 quedaría hoisteada
y habría dos React, el mismo problema que con Next.

- **El aviso de `fetchPriority` ya no aparece.** El bundle cliente lleva
  `ReactVersion = '18.3.1'` (`.next/static/chunks/main.js`), y en `/shops`
  con sesión el avatar sale como `<img alt="user name" fetchpriority="high"
  …>` (en minúscula) sin ningún aviso en consola.
- **Pero React 18.3.1 estrena otro aviso en el admin**, en el dashboard,
  `/products` y `/orders`:

  ```
  [error] Warning: %s: Support for defaultProps will be removed from function
  components in a future major release. Use JavaScript default parameters
  instead.%s Table
      at Table (webpack-internal:///../../node_modules/rc-table/es/Table.js:133:25)
      at RecentOrders / ProductList / OrderList ...
  ```

  `rc-table@7.22.2` define `Table.defaultProps` (`es/Table.js:695`). Es una
  deprecación que React 18.3 añade de cara a la 19. Con 18.2.0 no sale en
  ninguna de las tres rutas.

**Decisión:** CA-2 no admite avisos nuevos, así que `bcd6852` se revierte con
`d5c2739` y **el pin sigue en 18.2.0**. Al volver a 18.2.0, `/shops` con
sesión tampoco da el aviso de `fetchPriority` (Next 14.2 ya pasa el atributo
en minúscula). El pin, por tanto, ya no hace falta para lo que se puso, pero
quitarlo trae el aviso de `rc-table`. Ese cambio pasa a US-83 (React 19), que
tiene que subir o sustituir `rc-table` de todos modos.

### Hallazgo de US-78: `uuid` en la API

`apps/api/rest/src/payment/paypal-payment.service.ts:4` importa `uuid` sin
declararlo (`grep -c '"uuid"' apps/api/rest/package.json` → 0). En el árbol
principal se resuelve desde `apps/node_modules/uuid`, del workspace del
frontend. Tras los `yarn install` de esta US, `apps/node_modules/uuid` sigue
en la 11.1.1 y `just build-api` compila (`nest build`, exit 0, antes y
después). No cambia nada; no se arregló aquí porque es de `apps/api/rest`.
